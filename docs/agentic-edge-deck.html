BLUF · agentic workloads on edge silicon

The agent's brain is bandwidth-bound, not TOPS-bound.

Measured on five devices from an RTX 5090 down to an NXP i.MX95 edge SoC: an on-device agent's cost is set by memory bandwidth, CPU, and model size — not by the TOPS number on the box. That changes how you size an edge-AI product.

01

Generation rides on bandwidth

Decode re-streams the weights per token, so it's memory-bound: achieved bandwidth holds at 55–70% of each chip's rated peak while rated TOPS varies many-fold. The headline, armored: ~1.9× decode cost per model tier, three boards. measured derived

02

The NPU's job is the front-end

The NPU doesn't speed decode — decode is bandwidth-bound on CPU, GPU and NPU alike. It earns its area on prefill/perception: on i.MX95 the Neutron NPU offloads prefill 8.4×. sourced

03

Model size ≈ a 2× cost

+1 tier = ~1.9× decode + ~2× memory, invariant across three NVIDIA tiers (consistent with weight-streaming). And the biggest brains stop fitting the smallest boards. measured derived

04

So the sizing question flips

Not "how many TOPS" but "which tier can this board hold and feed" — then budget DDR + CPU for the generation loop and aim NPU TOPS at perception & first-token latency. derived

02 / 09

definition · two very different "agents"

Not all "agentic" wants the same silicon.

The word hides a 100× hardware split. Size for the one you're actually shipping.

(a) ships on-device today

Bounded skill-orchestrator

A fixed menu of tools — retrieve, transcribe, summarize, read/write files, call an API. A small on-device LLM (7B-class) is a capable enough brain. This is what Google Gemini Nano and Apple Intelligence ship. sourced

(b) wants a frontier brain

Autonomous code-gen / open-ended

Writes and runs novel code, plans open-endedly. Local-first in principle, but needs a large model to be good — today that's a cloud-scale brain, not an edge part.

This deck benchmarks (a) — the shippable case — using a local skill-orchestrator agent ("Skippy", Qwen 2.5 7B) as the reference. 7 of the 10 tasks are drawn from a general agent framework's capability set; 3 edge-perception tasks (transcribe, OCR, meeting→summary) were added.

04 / 09

the core physics

Decode is memory-bandwidth-bound.

Each generated token re-reads the whole model's weights from memory. So generation speed is set by how fast you can stream weights, not by peak math throughput. Prefill (the prompt / first token) is compute-bound and parallel — that's a different resource.

  • Generation-heavy tasks: ~85–90% of time in decode. measured
  • RAG/tool tasks: 51–70% decode, +37–47% in CPU/DDR orchestration. measured
  • Achieved bandwidth (decode × weights) = 55–70% of each chip's rated peak — the memory-bound signature; tok/s does not track TOPS. derived
cross-instrument corroboration — Hexagon NPU

Measured independently in our own program on a Qualcomm Hexagon NPU (a different runtime and silicon, by the qualcomm session):

"Decode is DDR-bandwidth-bound. The scarce resource for LLM/VLA decode is DDR bandwidth, not TOPS."

and the real limit is fit, not speed

Capacity + context, not TOPS.

On the iq9 the deployed NPU bundle caps a single prompt at 256 tokens — longer RAG context spikes TTFT to ~108 s on the CPU fallback. sourced A 14B on i.MX95 is untested and impractical (~1 tok/s projected). derived

Sizing an edge agent is fit-then-feed — capacity + context window + bandwidth, not the TOPS rating.

Clean passes: the grounded, perception & tool tasks — file I/O, transcribe, OCR, run-script. The 6 open-ended writing/RAG tasks are where it struggles: the judges split on four of them (spec-RAG, email, doc-brief, meeting) — the 7B's terse, hedged output lands borderline rather than clearly right.

14B base, same 10 tasks

08 / 09

where the NPU pays off

The accelerator's job is perception, not generation.

The NPU doesn't speed the generation loop — decode is bandwidth-bound on CPU, GPU and NPU alike. Where the accelerator genuinely earns its area is the compute-bound perception front-end:

  • Prefill / TTFT — on i.MX95 the Neutron NPU offloads prefill 8.4× (@L=512) while decode stays a CPU wash. The measured NXP proof-point. sourced
  • Vision / VLM / VLA — image prefill dominates, decode is tiny (the mirror image of the LLM tasks).
  • ASR and other parallel, compute-bound perception.

So an agentic edge SoC wants two separate budgets: DDR bandwidth + CPU for the generation loop, and NPU TOPS aimed at perception + first-token latency.

09 / 09

the decision

Size the subsystem, not the TOPS.

Not a benchmark — a design input for the next i.MX agentic part: size the subsystem (bandwidth, capacity, accelerator) to the model tier the product needs, and aim Neutron TOPS at perception, not the generation loop.

measured on NXP silicon

i.MX95 does a 7B — with its accelerator

Real FRDM board: bare A55 CPU 1.85 t/s; +ARA240 accelerator 6.3 t/s (≈ NXP's 6.51 spec), and Neutron offloads prefill 8.4×. The accelerator is what makes a 7B interactive — size it in, not out.

design floors · 7B tier

Feed the loop, don't starve it

A decode path delivering ≥~100 GB/s to the engine that runs it (CPU alone on i.MX95 reaches ~9), ≥~10 GB DRAM for weights + KV, and an accelerator for prefill/TTFT. TOPS sized to perception.

product rule

Fit-then-feed, per feature

A 7B orchestrator ships on small boards — it passes the grounded/perception/tool tasks cleanly. The open-ended-synthesis gap is a grounding problem, not a size one: a 14B fails those tasks harder (temp-0 two-judge). Fix it with RAG discipline, not parameters.

watch

Context length is the hidden cap

The iq9's 256-token NPU prompt cap is the binding constraint for RAG on the smallest parts — longer context silently falls to CPU (~108 s TTFT). Size the context window deliberately.
