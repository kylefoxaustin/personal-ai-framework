The whole story01 / 12

Agentic at the edge is bandwidth-bound, not TOPS-bound.

An on-device agent orchestrates a fixed, pre-tested set of skills — transcribe, retrieve, see, draft — it does not write and run new code. Every shipping on-device agent today works this way Sourced. Its cost is dominated by LLM decode, which is limited by memory bandwidth — so a 500-eTOPS NPU sits largely idle during agentic work.

Definition02 / 12

Two things are called "agentic." Only one ships on-device.

(a) Bounded skill-orchestrator ships

Intent → plan → execute a fixed, pre-tested toolset → synthesize. No new code. Deterministic, safe, benchmarkable.

= Skippy · Apple Intelligence · Gemini Nano · Snapdragon agentic

(b) Autonomous code-gen agent

Writes and runs novel code, full system access. Powerful — but wants a frontier brain and ships unvalidated code.

= OpenClaw · cloud agents · this fleet. Cloud / biggest-chip territory.

What ships today is (a), unanimously Sourced: Google's Gemini Nano exposes 4 fixed skills via per-task LoRA adapters; Apple's on-device ~3B model is explicitly "not a general chatbot" and uses constrained tool-calling that cannot hallucinate a tool name. No shipping product runs on-device code generation.

The edge product is the bounded orchestrator. The code-gen agent is the ceiling, and it lives in the cloud.

The reference agent03 / 12

A bounded edge agent, concretely: Skippy.

A full agentic assistant we built and instrumented — the measurable stand-in for the shippable edge product.

Fixed, tested skill registry

RAG retrieval · transcription (ASR) · OCR · document generation · email draft · calendar · reminders. Each is validated code the agent selects — never rewrites.

Multi-step orchestration loop

Detect tool → execute → feed result back, up to 5 steps, then synthesize. The "intelligence" is in routing + synthesis — exactly the LLM workload we measure.

Running on the RTX 5090 today; being ported down the ladder to Thor, Orin, and the i.MX95 class — so every number here is from a real app, not a projection.

Why bandwidth · 1 of 204 / 12

Agentic work is decode-dominated.

An LLM runs in two phases. Agentic tasks live almost entirely in the second one.

PhaseWhat it isShare of LLM timeBound by
Prefillread the prompt, in parallel1.1%compute / TOPS
Decodegenerate tokens, one at a time98.9%memory bandwidth

Decode is autoregressive and serial; the KV-cache is re-read every single token and grows with context. In real agentic traces, high cross-turn context reuse means little re-prefill — so decode consumes 91–98.6% of LLM time Sourced. We measured 98.9% on our own stack Measured.

decode_heavy, 7B v4 Q4 on 5090, n=3: decode 1731 ms vs prefill 20 ms.

Why bandwidth · 2 of 2 · the headline05 / 12

Decode is bandwidth-bound — so the NPU is idle.

Decode just streams weights from memory. Throughput is set by how fast you can read them — not by TOPS. Across the ladder, the same 7B's decode rate tracks memory bandwidth:

~220 t/s
Jetson Thor

The 500-eTOPS NPU does nothing for decode. It accelerates convolution-shaped perception; autoregressive decode is a bandwidth problem the NPU can't touch. Spending die area on TOPS to make an agent faster is spending it in the wrong place.

The second cost06 / 12

The agent is cheap. Orchestration and cold-start aren't.

Warm agentic task ≈ 2 s

~65% LLM / ~35% retrieval + orchestration (CPU + memory). The GPU/NPU sits near-idle for the retrieval third. The agent's cost isn't only the model.

Cold-start ≈ 89 s

50× the warm path. First query pays to load the embedding model + search index + vector DB. A device that sleeps and wakes pays this on every cold path.

So the NPU is idle twice over: decode is bandwidth-bound, and the orchestration layer is CPU/memory-bound. Design implication: keep models resident, and size CPU + memory for the retrieval/orchestration layer, not just the accelerator. Measured

Architecture08 / 12

One bounded agent — not a swarm.

Running multiple cooperating agents is tempting, but it's expensive on constrained silicon.

Each extra agent is another LLM context — more memory, more bandwidth contention, more cache thrash. A single well-scoped agent is the edge answer; multi-agent is justified only when the mission genuinely needs parallel, independent context. (That's the cloud/fleet model — the ceiling, not the edge product.)

So what11 / 12

What this means for NXP silicon.

Consumer

voice assistant, inbox. Bandwidth + CPU bound. Modest LLM accelerator; small NPU for wake-word/ASR.

Industrial

field-service, inspection. Vision NPU for perception + bandwidth for the RAG/reasoning agent.

Automotive

in-cabin + event reasoning. Sustained perception NPU + burst decode. Memory is the shared bottleneck.

The high-end part (16× A720, 500 eTOPS, 256-bit LPDDR5X) is sized correctly for perception. For the agent riding on top, the levers that matter are LPDDR5X bandwidth and CPU — not more TOPS.
